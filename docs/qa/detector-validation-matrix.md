## Identity feasibility result and next step

The API 36 pilot observed null IDs for Instagram `454.0.0.54.77` and YouTube `21.32.4`; it did not establish continuity or distinctness. Keep both exact versions unsupported. The next step is to evaluate another privacy-safe identity signal. Do not collect the full accuracy corpus until a candidate identity can be revalidated at the one-second deadline and distinguishes same-item from changed-item observations. [Android API reference](https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo#getUniqueId())

The API 36 alternative probe (2026-11-07) compared a per-node `hashCode()` handle, bounded child topology, and visible state with coarse bounds; only relation labels were retained. Instagram showed `same` for all three across two observed pager advances, so these signals did not distinguish the changed page. YouTube showed transient `changed` labels for the node handle and topology on two swipe attempts, then `same`; its visible-state signal changed more often during the swipe window. Neither gesture produced a pager-scroll event, so the YouTube item transition was not independently confirmed. These are feasibility observations only; both versions remain unsupported, and no profile or count behavior is enabled.

The 2026-11-07 logic update adds an estimated-only structural strategy that combines a candidate node handle with bounded child topology and rederives the pair from the current root at the dwell deadline. Later structural candidates also require a pager transition; topology change alone does not count. This is a mechanism for testing future profiles, not evidence that the pair identifies feed items. Instagram's observed pair stayed unchanged across the sampled page advances; YouTube's results remain inconclusive. No profile is enabled and the matrix statuses above are unchanged.

## Per-profile acceptance gate

For each exact app version, collect at least 200 labeled item transitions and 100 stationary/non-feed cases across at least three device families and the supported Android API range. Record true positives, false positives, false negatives, precision, recall, repeated stationary increments, test cases, and uncovered combinations. A profile becomes confirmed only with precision ≥98%, recall ≥90%, and zero repeated increments in the 100 stationary cases. Otherwise retain estimate-only or unsupported status.

## Data collection rules

- Ground truth uses human-labeled exposure events and coarse timestamps.
- Runtime evidence may contain selected package, app version, API/device family, event type, structural view IDs, pager indexes as transition evidence, and salted ephemeral identity hashes only.
- Do not capture or retain UI screenshots, feed text, message text, media, audio, OCR output, or plain item tokens.
- Each run requires the in-app disclosure and affirmative consent; the user enables/revokes Android Accessibility permission themselves.
- The 2026-11-07 device inventory used `adb devices -l`, `adb shell pm path <package>`, and `adb shell dumpsys package <package>` for package versions only. It did not enable Accessibility or collect feed observations.
- The later supervised RMX2156 probe used a debug-only, ten-minute marker and bounded structural TSV output. The user enabled Accessibility; the probe recorded only selected-app package/version, Android resource ID names, event type/index, and 100 ms monotonic timestamps. The two current package-validated entry fixtures and superseded exploratory files are described in `docs/qa/fixtures/README.md`; no content or screenshot was collected. On-device probe marker and output files were deleted after collection.
