# BrainPal reverse engineering findings

Status: static inspection plus bounded live testing of both counting routes. The accessibility block trigger, overlay callbacks and NFC blocking-state mutation, stats API contract and transport setup, EntryOnboarding option analytics path, generic questionnaire answer path, separate handoff state-to-analytics path, and UserPref Room write path are traced statically. Static analysis maps the shared counter's 750 ms dwell gate, five-minute de-duplication cache, fallback audio-derived candidate key, and per-app daily aggregation. Whether those candidate keys map one-to-one to actual Shorts remains unverified. Live block-screen behavior, persistence of individual EntryOnboarding selections, and actual network requests or transmitted values remain unresolved. The close callbacks and local NFC state mutation were not observed at runtime.

## Target and method

- BrainPal package `com.brainrot.android`, version `22.1.644` (version code `644`), pulled from Google Play while installed on the connected Realme RMX2156 (Android 12 / API 31).
- The base APK SHA-256 is `1447f2dfe73e7b9253bda4693b404f6e335e4b2dbf9068cbd74c06a9ed18eaff`. REA reports 14,092 classes and 954 resources. Static class/method analysis used REA CLI `6.8.0` and JADX headless `0.7.1`; complete REA Evidence records are in `evidence/`. The supplemental `apkanalyzer` tool version, commands, APK digest, and extract hashes are recorded in `evidence/apkanalyzer_trace_notes.md`.
- Static observations describe declarations and decompiled paths; they do not by themselves establish that a path ran or that data was transmitted. Runtime observations below come from the RM during a bounded, synthetic session.

### Reel observation and counting paths

- The manifest declares `ReelsAccessibilityService`. Its referenced XML config has event mask `0x401820` (window state changed, window content changed, view scrolled, and windows changed), `canRetrieveWindowContent=true`, and `canPerformGestures=true`. Its event handler records the foreground package and timestamp, handles a window-state event, and forwards packages in the app's monitored set. That set includes TikTok, TikTok Lite, YouTube, Instagram, Snapchat, and Facebook. The decoded config is `evidence/accessibility_service_config.xml` (SHA-256 `ae4fa785e8f23695e60d28cb9d591826a7c769dee094a251e7bb4a88342d733e`). REA's `decode-android-resources` could not run because the apktool launcher is absent (`evidence/android_resource_decode.json`); this XML was read from the APK using the existing Android SDK `apkanalyzer`. REA Evidence: `manifest_analysis.json` (`ev_ba85dad1934b0df7f2902f463c88e62dc9ab4d72d5d8e7792c0753f185ba7357`), `accessibility_class.json` (`ev_1bcd4dd14f835b5194bad3a996f544efcbdc744360cb71d2f444e399175b40d0`), `accessibility_on_event.json` (`ev_44cfd1638563f991723c43f0b0bc435e8e3fb0b6422eec12c707f5585d0957ee`), and `package_filter_init.json` (`ev_9030233a6688d15f299f9fb37b220e5e073b3932632ffcd2d9e8522265c8304f`). The static monitored set is broader than the Android disclosure's three named apps.
- When the Accessibility service connects, its code marks the service active, stops the fallback counter if that service was running, and calls analytics-related event and user-property wrappers. This is a static call path; it does not show that an analytics event reached a server. Evidence: `accessibility_service_connected.json` (`ev_2ca7ceeb8f7cf6c6302872d51f738421ca39fd2c900ec95e9571d20cdbf2ac28`).
- The fallback service polls `UsageStatsManager.queryEvents` over a rolling window and inspects active `AudioPlaybackConfiguration` entries. Its audio filter accepts usage `1`, then derives a candidate key from the package and the configuration's string form. The shared `uj.c0` tracker de-duplicates the composite app/key for five minutes and counts a tracked segment only when its dwell reaches 750 ms; finalization occurs on a candidate transition or app exit. Accepted segments increment a local per-day/per-app Room row, while the displayed daily total sums the app rows. The code therefore defines the timing and state gates, but not a one-to-one mapping from an audio configuration key to a Short. Details and extract hashes are in `evidence/fallback_counter_trace.md`. REA Evidence: `fallback_counter_tick.json` (`ev_edffca5f35632a3ae1750a2abd8dfa4211c426651a01e4957967de57d0f1b5af`), `fallback_counter_j.json` (`ev_278eb422661301814fbe994d32c17d3779ea96fbc87b93c598fd1503ec42cff7`), `fallback_counter_onstart.json` (`ev_bd39ba89945f40008c4b26b7d9b93f66987e9747477e18548399e0c346435b88`), and `fallback_counter_emit.json` (`ev_34b6b34b63e7a3f5dd46a972f452adc468b0ca791831900da2bfdf93890a5bb1`).
- `ReelsCounterFloatingService.onCreate` checks `Settings.canDrawOverlays`; if access is missing it logs a warning and stops. If allowed, it attempts to create/show the bubble. Evidence: `floating_service_oncreate.json` (`ev_a734d262ce62349d9f85e1583d736597aec49736756dc2f472a9a5444a54958a`).
- The accessibility block trigger now has a focused static trace. `ReelsAccessibilityService` combines the monitored app identifier with an extracted reel token and asks `uj.c0.i` whether to count it. The de-duplication helper returns `COUNT`, `SKIP_CURRENT_VIDEO`, or `SKIP_RECENTLY_COUNTED`; the latter cache prunes entries older than 300,000 ms (five minutes). A skipped item is considered for blocking only when its composite key differs from the immediately previous key, so an immediate repeat is skipped while a recently seen reel revisited after another reel reaches the block-decision use case. The use case maps `BLOCK_ACTIVE` and `REELS_LIMIT_REACHED` to `SHOW_BLOCK_ACTIVE`, and `REELS_EXHAUSTED` to `SHOW_REELS_EXHAUSTED`; other statuses produce no overlay decision. This is static behavior, not a confirmed runtime launch. The focused `apkanalyzer` Smali extracts are in `evidence/apkanalyzer_reel_dedupe.smali.txt` and `evidence/apkanalyzer_block_decision.smali.txt`.
- The launch path is now traced from the service event to `BlockReelsOverlayActivity`: it forwards the `source_app_id`, avoids a duplicate/recent launch when the block screen is already foreground or was launched within five seconds, stops the floating counter if active, then starts the overlay. `onNewIntent` queues the source app ID and logs if the fresh-launch event is dropped. The activity’s `onCreate` configures portrait orientation (except on API 26), adjusts system-bar behavior, and installs its UI content. The static UI strings include “Exit Reels,” “Use other options,” “Allow %1$d Reels,” and “Unlocks in.” The “Exit Reels” callback logs `BLOCK_REELS_OVERLAY_CLOSE_CLICKED` and emits `CloseOverlay(resumeReels=false)`. The NFC “Use other options” callback logs `BLOCK_REELS_NFC_LIMIT_DONE_CLICKED`, writes the current time to `last_limit_respected_at_v1`, then emits the same close event. The generated Activity callback bridge maps `false` to `PERFORM_BACK` and `true` to `PLAY_MEDIA`, broadcasts the action to the accessibility service, then finishes the overlay Activity. `PERFORM_BACK` waits 500 ms and, while the accessibility service is active, calls Android's global Back action. `PLAY_MEDIA` waits 500 ms and dispatches a 50 ms accessibility tap at the display center; it is not a media-key command, and the foreground app's response is unknown. These paths are static only; neither control action nor an overlay launch was observed during the RM test. Existing REA evidence: `class_block_reels_overlay.json` (`ev_719961f35ff394c875f4ae4943b1e51f7386ed107bdba72b631070723af64183`) and `block_overlay_oncreate.json` (`ev_03ba2686835a204855d23e91a87329a903ba547baae51bd0ce9cec0187683412`). Supplementary extracts: `evidence/apkanalyzer_block_trigger.smali.txt`, `evidence/apkanalyzer_block_launch.smali.txt`, and `evidence/apkanalyzer_block_controls_trace.md`; the method-level callback extracts are in `scratch/block_ui_g1_m1.smali`, `scratch/dd_d.smali`, and `scratch/cb_e.smali`.

- The NFC button's state mutation is now field-mapped: when a current blocking record exists, the handler sets `isBlockEnabled=true`, clears pause expiry, block-start time/count, and hard-block expiry, and updates `updatedAt`; it preserves the current allowed reel count, cooldown, and allowed-window duration. The result passes through the local `UserBlockingConfig` repository (`user_blocking_config`). If the record is absent, it creates an enabled default record instead. Static extracts and mapping are in `evidence/apkanalyzer_nfc_state_update.md`. Runtime execution and network transmission remain unobserved.

### Onboarding answer handling

#### EntryOnboarding path used on the RM

- The RM's first two questions map to `Lng/r` IDs `q1_when` and `q2_screen_time`. Their option enums are `Lng/e0` (`all_day`, `bored`, `study_work`, `after_dinner`, `late_night`) and `Lng/d0` (`under_3`, `3_6`, `6_9`, `9_plus`). The resource table maps `entry_ob_q1_bored` to “When I'm bored” and `entry_ob_q2_3_6` to “3–6 hours”; the DEX resource-reference scan points both IDs to `Lng/l;->h`. The full resource scan is `evidence/apkanalyzer_onboarding_resource_refs.json` (SHA-256 `889c32214b92f0b897d56e3cdb8e3ac2d29b1a9cf17bebf878335b4f8e070a0c`).
- `jg.n.c(jg.j)` sends `ENTRY_ONBOARDING_SCREEN_SHOWN` with the active screen ID. `jg.n.c(jg.f)` validates option IDs against the current question's choice list, enforces the question's single/multi-select flag, updates the answers map in `jg.l`, derives `EntryAnswers` (`ng.h`), and replaces the ViewModel's `StateFlow` value. For each changed option it calls the analytics repository with `ENTRY_ONBOARDING_OPTION_SELECTED` and fields `screen`, `option`, `selected`, and comma-joined `picks`. On this path the RM's synthetic picks would be represented as `screen=q1_when, option=bored, selected=true, picks=bored` and `screen=q2_screen_time, option=3_6, selected=true, picks=3_6` if the corresponding handlers ran. The continue action also has an `ENTRY_ONBOARDING_CONTINUE_CLICKED` path with the current screen ID.
- The completion coroutine `hi.l0.invokeSuspend` dispatches `ENTRY_ONBOARDING_COMPLETED` with a JSON payload containing only the final `limit` answer. The Q1 and Q2 choices are absent from that completion payload; their only traced answer-bearing analytics payload is the per-option selection event above. This remains static call-path evidence, not a captured event.
- The inspected selection reducer updates the ViewModel answer map and dispatches analytics; it contains no direct Room write. The local preference boundary is now verified: `UserPrefDatabase_Impl` registers `user_pref_boolean` and `user_pref_string`, `ka.r` supplies their Room table DDL, and the insertion adapter uses `INSERT OR REPLACE`. On completion, `hi.l0.invokeSuspend` writes `br_onboarding_questions_done_v1=true` through the boolean preference path, then calls `jg.n.a`. That writer reads `Ljg/l.e` (`Lng/p`) and writes `br_entry_dream_path_v1` and `br_onboarding_plan_v1`; it does not read the selected-option map `Ljg/l.b` or the derived EntryAnswers record `Ljg/l.d`. The completion analytics event separately reads the last answer group's `limit` and emits only that field. Within these inspected paths, the individual Q1/Q2 picks are not shown written to Room; they are held in ViewModel state and included in option-selection analytics payloads. This does not rule out other untraced persistence or establish that analytics ran or reached a server. The RM was left on Q3 health without an answer, so onboarding completion was not observed. Supporting persistence extracts and bounded field-reference scans are documented in `evidence/apkanalyzer_preferences_trace.md`; the original onboarding decompilations are in `scratch/entry_jg_n.smali`, `scratch/entry_jg_l.smali`, `scratch/entry_hi_l0.smali`, `scratch/entry_jg_f.smali`, `scratch/entry_jg_h.smali`, `scratch/entry_ng_r.smali`, `scratch/entry_ng_e0.smali`, `scratch/entry_ng_d0.smali`, and `scratch/entry_ng_l.smali`.

- Static DEX definitions contain eight answer groups: life stage, primary scrolling app, estimated scroll hours, goal, peak scroll time, after-scroll feeling, daily reel limit, and reel recall. Their string property keys are `br_life_stage`, `br_main_scroll_app`, `br_self_estimate_hours`, `br_goal`, `br_peak_scroll_time`, `br_after_scroll_feeling`, `br_daily_reel_limit`, and `br_reel_recall`. The accepted values and single/multi-select flags are in `evidence/apkanalyzer_onboarding_trace.md`.
- A separate static handoff model, `Lvg/o0;`, builds `Lvg/e0` options from `onboarding_handoff_*` resources. It includes `when_bored` and hour identifiers that overlap with the generic questionnaire; those values are separate from the RM's EntryOnboarding picks above. The `Lvg/n;` ViewModel state contains selected option IDs in a map, and `Lvg/y;.m` serializes the map into `handoff_selected_option_ids` plus a count and page identifiers. Static handlers send `ONBOARDING_HANDOFF_SCREEN_SHOWN` and `ONBOARDING_HANDOFF_CONTINUE_CLICKED` events with that JSON to `oc.d`. This makes the selected options part of an outbound-capable analytics path; execution and transmission were not observed. The separately declared `kc.a.q3` event, `ONBOARDING_HANDOFF_OPTION_SELECTED`, has only its enum initialization and values-table/accessor reference in the bounded direct DEX scan; no business-code caller was identified. Indirect dispatch remains possible, so this does not prove the event unused. Durable handoff-answer storage remains unknown. Evidence: `evidence/apkanalyzer_handoff_options.smali.txt`, `evidence/apkanalyzer_handoff_event_refs.json`, and `evidence/apkanalyzer_handoff_state.smali.txt`.
- `eh.e.w` filters selections against each group's accepted values, comma-joins them, and forwards the answer under the group's `br_*` key. When `other` is selected and free text is nonblank, it also forwards `<key>_other` with trimmed text. The handler builds an `ONBOARDING_QUESTION_ANSWERED` event containing `question`, `answer`, `answer_count`, optional `answer_text`, and `placement`.
- The answer handler calls a subscription-state manager that caches each key/value in memory and calls RevenueCat `Purchases.setAttributes` if RevenueCat is configured. The event is sent to the app's asynchronous analytics repository; its code contains Firebase Analytics and Meta queue paths. This is evidence of outbound-capable SDK paths, not a captured request or proof that both SDKs transmit this particular event.
- The inspected answer methods do not directly write through Room, SQLite, or Android Preferences. Durable local answer storage remains unresolved because other code could persist the values. Static evidence cannot confirm whether the queued answers left the device.
- Focused static evidence: `evidence/apkanalyzer_onboarding_trace.smali.txt` and the literal resource-ID cross-reference `evidence/apkanalyzer_onboarding_resource_refs.json`. These are supplementary `apkanalyzer`/DEX artifacts and have no REA Evidence IDs.

### Network and analytics surface

- The manifest declares `INTERNET` and `ACCESS_NETWORK_STATE`, as well as `SYSTEM_ALERT_WINDOW` and `PACKAGE_USAGE_STATS`. Other declared permissions are recorded in `manifest_analysis.json` (`ev_ba85dad1934b0df7f2902f463c88e62dc9ab4d72d5d8e7792c0753f185ba7357`).
- `BrainRotStatsApiService` declares these routes: `GET /stats/api/v1/user/config`, `POST /stats/api/v1/user/config/update`, `POST /stats/api/v1/user/scroll/update`, `POST /stats/register_sync_user`, `GET /stats/api/v1/user/restore`, plus three duel/friends reads. Its Retrofit builder reads `AuthConfig.serverBaseUrl`; the Dagger factory constructs that config with the APK literal `https://api.brainpalapp.ai`, which is the static stats-service host for this build. A separate provider also uses `https://api.brainpalapp.ai/` for the feedback client. The focused provider trace is in `scratch/jc_y_full.smali` and is documented in `evidence/apkanalyzer_network_client_trace.md`.
- The stats client starts from an OkHttp client with an auth interceptor. Static code reads the stored `access_token` and sets `Authorization: Bearer …`; on HTTP 401 it can use the stored refresh token and `AuthApiService`, save refreshed tokens, and retry. The stats-specific interceptor adds `android_device_id` (sourced from `Settings.Secure.ANDROID_ID` and persisted in `brain_rot_instance_prefs` as `app_instance_android_id`), optional `br_user_id` from the auth profile, `br_app_id=com.brainrot.android`, `app_version=22.1.644`, and `app_version_code=644`. A second stats-client interceptor uses an `http_swr_cache` directory. These are static paths; they do not establish that any request ran. The token-storage factory also contains a fallback from encrypted to regular SharedPreferences; whether it takes that fallback on the RM is unknown. Focused `apkanalyzer` extracts and hashes are recorded in `evidence/apkanalyzer_network_client_trace.md`.
- The `updateScrollStats` call path builds a `ScrollUpdateRequest` with `android_device_id`, `stats_date`, and a `splits` list. Each split contains `app_package`, display name, reel count, and view duration, sourced from local daily app splits. This endpoint’s declared body is aggregated per app/day and has no individual reel identifier field. `updateReelsConfig` accepts a `BlockReelsState` body and an `android_device_id` query parameter; that model includes block-enabled state, allowed reel count, quota/cooldown windows, pause and start timestamps/counts, hard-block validity, pinned friend ID, and update time. Static call paths were found for scroll sync and block-config update; interface declarations or call paths do not prove a request ran or identify all headers/interceptor data. Full focused extracts: `evidence/apkanalyzer_stats_api.smali.txt`. Existing REA evidence: `class_brainrot_stats_api.json` (`ev_9406d3ec9a38d5ee1050e0ab1ec1d2c4b2760d41381a55ebcae04364c831690b`) and `api_get_reels_config.json` (`ev_4532ab956a1d04bc458cf5dc54ca44ebfc596bd99ee3bffd415dfb6974c00e3a`).

These are static indications only. No BrainPal traffic was captured, so collection and transmission are not established.
